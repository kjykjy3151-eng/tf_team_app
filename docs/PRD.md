# PRD: 팀 프로젝트 팀 편성 웹 앱

기준 문서는 `참고자료/공고.pdf`이다. 이 PRD와 공고가 다르면 공고를 따르고, 다르게 만들어야 할 것 같으면 먼저 확인한다. 각 절 제목 옆의 괄호는 공고의 절 번호다.

## 0. 개요 (공고 1장)

- 학생들이 팀 프로젝트용 팀을 스스로 편성하는 웹 앱을 만든다. 모집 마감 뒤 남은 학생의 배정은 AI가 돕고, 앱이 AI의 답을 규칙으로 검사한다.
- 기술: Streamlit 앱, Supabase DB(PostgreSQL), 오픈라우터 AI, Streamlit Community Cloud 배포.
- 마감: 11/2(월) 23:59. 채점 기간: 11/3(화)~11/4(수). 채점 기간에 DB가 일시정지되어 있으면 안 된다.
- 채점: 배포한 앱에서 공개하지 않은 채점 시나리오 3개(쉬움, 중간, 어려움)를 자동 채점 프로그램이 실행한다. 부록의 시나리오 3개는 연습용이다.
- 비용 원칙(사용자 요구): 사용자에게 비용이 하나도 들지 않아야 한다. AI는 무료 모델(`:free`)만, DB와 배포는 무료 요금제 범위 안에서만 쓴다.

## 1. 등장인물 (2.1)

"학생"은 명단 CSV의 가상 학생이다. 앱을 만드는 사람은 시험할 때 가상 학생과 관리자로 번갈아 로그인해 확인한다.

| 사용자 | 하는 일 |
|---|---|
| 학생 | 학번과 비밀번호로 로그인한다. 팀 목록과 팀원, 팀원의 주 역할과 보조 역할을 본다. 팀에 지원한다. 내 팀에 들어온 지원에 찬성 또는 거부를 누른다. |
| 관리자(교수) | 학번 `admin`으로 로그인한다. 명단을 올려 처음 상태를 만든다. 모집을 마감한다. 마감 뒤 남은 학생의 배정안을 받아 확인하고 확정한다. |

- 관리자 계정은 앱이 시작할 때 비밀 값 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신한다.
- 명단을 다시 올려도 관리자 계정은 남긴다.

## 2. 명단과 역할 (2.2)

- 학생 명단은 관리자가 CSV 파일로 올린다(6장). 학생의 비밀번호는 모두 `1234`다.
- 실제 학생의 이름과 학번은 쓰지 않는다. 교수가 나눠 주는 가상 명단만 쓴다.
- 역할은 6개다: 기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자.
- 학생마다 주 역할 1개와 보조 역할 0~2개가 CSV에 정해져 있다. 학생이 바꾸지 않는다.

## 3. 팀 규칙 (2.3)

| 규칙 | 내용 |
|---|---|
| 팀 | 관리자가 명단을 올릴 때 넣은 팀 수만큼 팀을 만든다(팀1, 팀2, …). |
| 인원 | 마감 뒤 확정한 팀 구성에서 모든 팀이 2~4명이어야 한다(빈 팀 없음). |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 된다. |
| 필수 포함 역할 | 확정한 팀 구성에서 모든 팀에 기획자 역할 학생과 웹 프로그래머 역할 학생이 서로 다른 사람으로 1명씩 있어야 한다. 주 역할이나 보조 역할로 맡을 수 있다. |

- 주 역할은 팀 안의 중복을 따지는 기준이고, 보조 역할은 필수 포함 역할을 맡을 수 있는지 따질 때만 쓴다.
- 예: 주 역할이 테스터이고 보조 역할이 기획자인 학생은 그 팀의 기획자를 맡을 수 있다.
- 지원과 투표 결과로 필수 포함 역할을 지킬 수 없는 팀이 생길 수 있다. 예: 웹 프로그래머를 맡을 수 있는 학생 없이 4명이 다 찬 팀은 더 넣을 수 없고, 마감 뒤 배정에서도 기존 팀원을 옮기지 않으므로 끝까지 채울 수 없다.

## 4. 지원과 투표 (2.4)

| 상황 | 규칙 |
|---|---|
| 빈 팀에 지원 | 투표할 팀원이 없으므로 바로 승인된다. |
| 팀원이 있는 팀에 지원 | 대기. 그 팀의 팀원 모두가 투표한다. 투표할 사람은 투표하는 때의 팀원이다(내가 지원한 뒤 다른 지원자가 먼저 승인되어 팀원이 되면, 그 사람도 내 지원에 투표한다). |
| 모든 팀원이 찬성 | 승인된다. 그 팀의 팀원이 된다. |
| 한 명이라도 거부 | 다른 팀원의 투표를 기다리지 않고 바로 거절된다. |
| 아직 투표하지 않은 팀원이 있음 | 대기. |
| 승인 직전 | 모든 팀원이 찬성해 승인하려는 때에 규칙(정원, 주 역할 중복, 필수 포함 역할 자리)을 다시 검사한다. 어기게 되면 그 지원은 거절된다. 그 전에는 대기 중인 지원을 미리 거절하지 않는다. (3장 표 "같은 팀에 대기 중인 지원이 여럿"의 어려운 해결) |
| 한 학생의 지원 | 지원한 팀의 결과(승인 또는 거절)가 나오기 전에는 다른 팀에 지원할 수 없다. 결과가 나온 뒤에는 다시 지원할 수 있다. |
| 팀이 꽉 참 | 4명인 팀에는 지원할 수 없다. |
| 같은 주 역할 | 주 역할이 중복되는 팀원이 있는 팀에는 지원할 수 없다. |
| 이미 팀이 있음 | 다른 팀에 다시 지원할 수 없다. |
| 막힌 지원 | 지원 단추를 누른 순간 앱이 규칙을 검사해 지원을 접수하지 않는 것. 이유: 팀이 꽉 참, 같은 주 역할의 팀원이 있음, 이미 팀이 있거나 결과를 기다리는 지원이 있음, 모집이 마감됨, 필수 포함 역할을 맡을 학생의 자리가 모자람(어려운 해결을 한 경우). 안내는 "막힘"으로 시작하고 이유를 함께 보여 준다(예: "막힘: 같은 주 역할의 팀원이 있음"). 투표 없이 끝나며 DB에 기록하지 않아도 된다. |
| 막힘과 거절의 차이 | 막힘은 지원을 아예 접수하지 않은 것이다. 거절은 접수되어 대기 중이던 지원이 팀원의 거부, 승인 직전 검사, 모집 마감으로 떨어진 것이다(안내는 "거절"로 시작). |
| 투표 바꾸기 | 한 번 투표하면 바꿀 수 없다. |

## 5. 마감과 배정 (2.5)

1. 관리자가 "모집 마감"을 누른다. 그 뒤로는 지원과 투표를 할 수 없다.
2. 마감 때 대기 중인 지원은 거절된다. 1명뿐인 팀의 학생은 팀에서 빠져 "팀이 없는 학생"이 된다.
3. 관리자가 "AI 배정"을 누르면 앱이 AI에게 지금의 팀 구성, 팀이 없는 학생과 그 역할, 3절(공고 2.3)의 규칙을 보내 배정안을 받는다. AI는 오픈라우터의 텍스트 생성 모델을 쓴다(12절). 팀이 없는 학생만 팀에 넣고, 이미 팀에 있는 학생은 옮기지 않는다.
4. 앱이 배정안을 다섯 가지로 검사한다.
   1. 팀이 없는 학생이 빠짐없이 배정됨
   2. 한 학생은 한 팀에만 배정됨
   3. 모든 팀이 2~4명
   4. 팀 안에서 주 역할 중복 없음
   5. 필수 포함 역할 충족
5. AI가 응답하지 않거나, 빈 응답이나 오류를 내거나, 배정안이 4항의 검사를 통과하지 못하면 앱이 자동으로 2차 모델, 3차 모델 순으로 다시 배정한다. 모델 하나를 부른 때부터 응답을 받을 때까지 120초가 넘으면 끊고 다음 모델로 넘어간다.
6. 3차 모델까지 실패하면 앱이 스스로 배정한다(9절 표).
7. 검사를 통과한 배정안만 관리자에게 보여 준다(학생의 이름과 역할, 배정된 팀). 관리자가 확정하면 DB에 저장한다.
8. 규칙을 모두 지키는 배정이 없으면 배정안을 만들지 않고, 관리자 화면에 "규칙을 지키는 배정이 없음"과 그 이유(예: 팀3에 웹 프로그래머를 맡을 학생이 없음)를 보여 준다. 이때는 AI를 부르지 않아도 된다.

## 6. 명단 올리기 (2.6)

- 관리자 화면에서 명단 CSV 파일과 팀 수를 넣으면 앱 상태가 초기화된다: 지원, 투표, 팀원, 마감 표시를 모두 지우고, 명단의 학생과 넣은 팀 수만큼의 빈 팀을 만든다.
- 채점자는 이 기능으로 시나리오마다 명단을 바꾼다. 이 기능이 없으면 채점할 수 없다.
- CSV는 BOM이 붙은 UTF-8이다. 앱은 BOM이 있는 파일도 읽어야 한다(`utf-8-sig`로 읽는다).

CSV 형식:

```
student_no,name,main_role,sub_roles
2026001,가나다,기획자,보고서 작성자
2026002,라마바,웹 프로그래머,
2026003,사아자,테스터,기획자;발표자
```

- `sub_roles`가 2개면 `;`로 구분하고, 없으면 마지막 쉼표 뒤를 비워 둔다. 쉼표를 지우면 열이 3개가 되어 CSV가 틀린다.

## 7. 화면 이름 표 (2.7)

자동 채점 프로그램은 화면 요소를 Streamlit의 `key`로 찾는다. 아래 표의 요소마다 `key`를 **표에 적힌 그대로** 지정한다. 화면에 보이는 글자는 자유롭게 써도 된다.

| 화면 요소 | Streamlit 요소 | key |
|---|---|---|
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input` | `login_password` |
| 로그인 단추 | `st.button` 또는 `st.form_submit_button` | `login_submit` |
| 로그인한 사람 표시(이름이 보임) | `st.container` | `whoami` |
| 단추를 누른 결과 안내 | `st.container` | `result` |
| 팀 하나의 표시(팀원의 이름이 보임) | `st.container` | `team_1`, `team_2`, … |
| 팀에 지원하는 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 지원에 찬성하는 단추 | `st.button` | `vote_yes_{지원자 학번}` 예: `vote_yes_2026306` |
| 지원에 거부하는 단추 | `st.button` | `vote_no_{지원자 학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 명단으로 처음 상태 만들기 단추 | `st.button` | `admin_start` |
| 모집 마감 단추 | `st.button` | `admin_close` |
| 팀이 없는 학생 표시(이름이 보임) | `st.container` | `unassigned` |
| AI 배정 단추 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 단추 | `st.button` | `admin_confirm` |
| 새로 고침 단추(3장 "다른 사람의 변경 보기"를 쉬운 해결로 만든 앱만) | `st.button` | `refresh` |

표에 딸린 규칙:

- `key`에는 영문, 숫자, 밑줄만 쓴다. 한글 `key`는 채점 프로그램이 찾지 못한다.
- `{지원자 학번}`은 그 지원을 한 학생의 학번으로 바꿔 넣는다(예: `vote_yes_2026306`).
- `team_1`의 1은 관리자가 명단을 올릴 때 만든 팀1, 팀2, …의 번호이며 시나리오의 팀 번호와 같다.
- `refresh`: 다른 사람의 변경 보기를 쉬운 해결로 만든 앱은 이 단추를 학생 화면과 관리자 화면에 모두 둔다. 채점 프로그램은 화면을 다시 열지 않고, 동작하기 전에 이 단추가 있으면 먼저 누른다.
- 자동으로 다시 표시하는 앱은 5초 이하 간격으로 다시 그린다. 채점 프로그램은 단추가 나타나기를 7초까지 기다린다.
- `result`는 단추를 누른 사람의 화면에 보인다. 지원 단추를 누르면 그 지원의 결과를, 찬성이나 거부 단추를 누르면 그 지원의 지금 상태(승인, 대기, 거절)를 보여 준다. 한 단계에 동작이 여럿이면 채점 프로그램은 동작마다 `result`를 확인한다.
- `result`의 안내는 "승인", "대기", "거절", "막힘" 가운데 하나로 시작한다. 예: "막힘: 같은 주 역할의 팀원이 있음"
- 관리자 단추(명단 올리기, 모집 마감, AI 배정, 확정)의 `result`도 해냈으면 "승인", 하지 못했으면 "막힘"으로 시작한다. 예: "승인: 모집을 마감함"
- 마감 때 대기 지원이 거절되고 1명뿐인 팀의 학생이 빠진 결과는 관리자 화면의 `unassigned`로 확인한다. `unassigned`에는 팀이 없는 학생의 이름을 보여 준다.
- 규칙을 지키는 배정이 없을 때의 안내(5절 8항)는 `assign_status` 안에 보여 준다.
- 이미 팀이 있음, 결과를 기다리는 지원이 있음, 모집 마감인 경우에는 지원 단추를 숨기거나 비활성화한다. 그 밖에 막히는 지원(같은 주 역할 등)은 누른 뒤 "막힘" 안내로 막아도 되고 단추를 숨겨도 된다. 채점 프로그램은 단추가 없거나 비활성이면 "막힘"으로 본다.
- `st.container`에도 `key`를 지정한다(예: 결과 안내는 `key="result"`인 `st.container` 안에 보여 준다).
- `key`를 표와 다르게 지정하거나 지정하지 않아 채점 프로그램이 멈추면 5점을 감점한다(13절 15번).

## 8. 학생 화면 (2.8)

- 팀 목록에서 로그인한 학생의 팀을 구별되게 표시한다(예: 팀 이름 옆에 "내 팀"). 팀이 없으면 "아직 팀이 없음"을 보여 준다(채점하지 않음).
- 이미 팀에 속했거나, 결과를 기다리는 지원이 있거나, 모집이 마감되었으면 지원 단추를 숨기거나 비활성화한다.
- 이미 투표한 지원에 대해서는 그 학생의 찬성, 거부 단추를 숨기거나 비활성화하고 "내 투표: 찬성"처럼 보여 준다.

## 9. 기능별 쉬운 해결과 어려운 해결 (3장)

아래 8가지 기능은 모두 만들어야 하며, 기능마다 쉬운 해결과 어려운 해결 가운데 하나를 고른다. 어느 쪽을 고를지는 구현 계획에서 정하고, README.md에 적는다(공고 7.1절 3항).

| # | 기능 | 쉬운 해결 | 어려운 해결 | 점수(쉬운, 어려운) |
|---|---|---|---|---|
| 1 | 다른 사람의 변경 보기 | 새로 고침 단추 | 바뀐 부분만 자동으로 다시 표시(`st.fragment`) | 0.5점, 1점 |
| 2 | 필수 포함 역할을 지킬 수 없는 팀 | 배정 단계에서 "규칙을 지키는 배정 없음"을 안내함 | 지원 단계에서, 필수 포함 역할을 채울 자리가 모자라게 되는 지원은 막음 | 1.5점, 7점 |
| 3 | 같은 팀에 대기 중인 지원이 여럿 | 지원할 때만 규칙을 검사하고 승인할 때는 다시 검사하지 않음 | 승인 직전에 규칙을 다시 검사함. 처리 순서는 지원한 순서가 아니라 투표가 끝난 순서 | 0점, 3점 |
| 4 | 마지막 자리에 두 명이 동시에 들어감 | 앱이 인원을 센 뒤 넣음 | DB의 유일성 제약으로 먼저 도착한 학생만 기록함 | 0점, 0.5점 |
| 5 | AI 응답이 늦을 때 | AI 요청 함수에 시간 제한 값(예: 120초)을 줌(응답 시작까지만 재는 경우가 많아 120초를 넘길 수 있음) | 모델마다 120초의 전체 대기 시간을 재서 끊고 다음 모델로 넘어감 | 0.5점, 1점 |
| 6 | 3차 모델까지 실패 | 자리가 남은 팀에 무작위로 넣음. 5절 4항 검사를 통과하지 못하면 그 사실을 함께 보여 줌 | 5절 4항의 검사 다섯 가지를 모두 통과하는 배정을, 모든 경우를 따져 끝까지 찾음 | 쉬운 해결은 확정 뒤 규칙 점수(최대 6.5점)를 잃을 수 있음 |
| 7 | AI 대기 중 화면 | "AI가 생각하는 중" 안내 | 몇 차 모델의 응답을 기다리는 중인지 보여 줌 | 0.5점, 1점 |
| 8 | DB(Supabase)가 일시정지되지 않게 | 제출 마감 날(11/2) 배포한 앱을 써서 DB 요청을 만듦 | 외부 예약 서비스로 매일 DB에 질의를 보냄 | 0점, 0.5점 |

표에 딸린 규칙:

- 점수 열은 공고 6.1절의 묶음 점수(30점) 안에 들어 있다. 1, 2, 3, 5, 7번은 어려움 시나리오, 4, 8번은 시나리오 밖이다. 6번의 6.5점은 중간 시나리오(2.5점)와 어려움 시나리오(4점)의 확정 뒤 규칙 점수를 더한 것이다.
- 필수 포함 역할 자리 계산: 지원자가 들어간 뒤 남는 자리 수가 그 팀에서 아직 채우지 못한 필수 포함 역할 수보다 적으면 지원을 막는다. 기획자와 웹 프로그래머는 서로 다른 학생이 맡아야 하므로, 한 학생이 둘 다 할 수 있어도 하나로만 센다.
  - 예: 주 역할 기획자, 보조 역할 웹 프로그래머인 학생 혼자 있는 팀은 필수 포함 역할 2개 가운데 1개만 채운 것이다.
  - 예: 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면, 남는 자리 1개로 필수 포함 역할 2개를 채울 수 없으므로 막는다.
- 4번은 채점 프로그램이 직접 만들지 않고, DB 유일성 제약이 있는지만 `schema.sql`로 확인한다.
- 앱이 잠들면 채점자가 깨운다. DB는 1주일 동안 요청이 적으면 일시정지되고 채점자가 다시 켤 수 없으므로, 12절(공고 4.4)의 방법으로 채점 기간 전 1주일 안에 DB를 써야 한다.
- 로그인은 학번과 비밀번호로 한다. 비밀번호는 해시로 저장한다(파이썬 `bcrypt`). 구글 로그인(`st.login`)은 쓰지 않는다.

## 10. 키 관리 (4.1)

- 오픈라우터 키, DB 주소, 관리자 비밀번호는 `.env` 파일에 두고, 배포한 앱에서는 같은 이름으로 Streamlit Secrets에 둔다.

```
OPENROUTER_API_KEY="sk-or-v1-자기 키"
DATABASE_URL="Supabase에서 복사한 DB 주소"
ADMIN_PASSWORD="정한 관리자 비밀번호"
```

- `.env`는 앱 파일(예: `streamlit_app.py`)과 같은 폴더에 둔다. 파일 이름은 정확히 `.env`여야 한다(`.env.txt`면 `.gitignore`가 걸러 내지 못한다).
- `.env`를 두 번 눌러 열지 않는다.
- 키 값을 화면에 출력하지 않는다. 키가 있는지 확인할 때는 "있음, 없음"만 출력한다.
- 키나 관리자 비밀번호를 코드에 직접 적거나 깃허브에 올리면(커밋 기록 포함) 감점한다.

## 11. DB (4.2, 5장)

### 11.1 원칙 (4.2)

- 6장 실습에서 만든 Supabase 프로젝트를 재사용한다. 6장 실습 전이면 노트 6장의 절차로 만들고 6장 실습에도 그 프로젝트를 쓴다. 새 프로젝트를 더 만들지 않는다(무료 프로젝트는 2개까지).
- 이 과제의 테이블 이름은 모두 `tf_`로 시작한다.
- 최소 참고안을 그대로 써도 되고 고쳐서 늘려도 된다(예: 지원 시각, 거절 이유 열, AI 호출 기록 테이블 `tf_ai_logs`).
- DB 연결은 한 번만 만들고 그 연결로 여러 번 질의한다. 질의마다 연결을 새로 만들면 화면이 몇 초씩 느려진다.

### 11.2 최소 참고안 (5장)

| 테이블 | 열 | 뜻 |
|---|---|---|
| `tf_students` | `id`, `student_no`(학번, 유일), `name`, `main_role`, `password_hash`, `is_admin` | 학생과 관리자 |
| `tf_student_sub_roles` | `student_id`, `role` | 보조 역할. 학생 1명에 0~2행 |
| `tf_teams` | `id`, `name`(유일) | 팀 |
| `tf_members` | `team_id`, `slot_no`(1~4), `student_id`(유일) | 팀원. `(team_id, slot_no)`를 기본 키로 둠 |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`(대기, 승인, 거절), `reason`, `created_at` | 지원 |
| `tf_votes` | `application_id`, `voter_id`, `vote`(찬성, 거부) | 투표. `(application_id, voter_id)`를 기본 키로 둠 |
| `tf_settings` | `key`, `value` | 마감 여부 등 |

- `tf_members`의 `(team_id, slot_no)`와 `student_id` 유일성 제약이 "먼저 도착한 학생만 기록"과 "한 학생은 한 팀에 소속"을 DB에서 지킨다.
- `slot_no`에 `check (slot_no between 1 and 4)`를 둬 다섯 번째 자리를 막는다.
- `main_role`과 `role`에 `check (... in ('기획자', '웹 프로그래머', ...))`를 둬 6개 역할 밖의 값을 막는다.
- 테이블을 만드는 SQL을 저장소의 `schema.sql`로 남긴다. 채점자는 이 파일로 유일성 제약, 테이블 이름(13절 13번), 비밀번호 해시 열(13절 10번)을 확인한다. 파일이 없으면 유일성 제약 점수(0.5점)를 받지 못하고 13번, 10번 감점을 적용한다.
- `schema.sql`은 앱이 실제로 쓰는 테이블, 열, 제약과 같아야 한다. Supabase SQL 편집기에서 직접 만든 SQL도 넣는다.

## 12. AI 모델과 배포 (4.3, 4.4)

### 12.1 AI 모델 (4.3)

- 오픈라우터의 텍스트 생성 모델 3개를 1차, 2차, 3차로 정해 쓴다. 비용 원칙에 따라 이름이 `:free`로 끝나는 무료 모델만 쓴다.
- 앞 모델이 실패하면(120초 넘음, HTTP 429, 빈 응답, 오류, 검사 불통과) 다음 모델로 넘어간다.
- 무료 모델 자동 라우터(`openrouter/free`)는 쓰지 않는다(13절 14번).
- 추론 모델의 빈 응답을 줄이려고 요청에 reasoning effort를 low로 주고 `max_tokens`를 넉넉히 준다. 빈 응답도 실패로 처리한다.
- 무료 모델은 계정마다 하루 50회, 분당 20회까지다. 실패한 호출도 센다. 채점 기간(11/3~11/4)에는 하루 한도 가운데 30번 이상을 남겨 둔다. 연습용 시나리오 3개를 한 번 돌리는 데 3~9번 든다.
- 무료 모델은 1~3분 걸리거나 쓸 수 없기도 하므로 3차까지 실패하면 앱이 스스로 배정한다.
- 채점은 확정한 팀 구성이 규칙을 지키는지와 실패 처리(모델마다 120초 제한, 2차와 3차로 넘어감, 3차까지 실패하면 앱이 스스로 배정)를 화면 기록이나 코드로 확인한다.

### 12.2 배포, 앱 잠자기, DB 일시정지 (4.4)

- Streamlit Community Cloud에 배포한다. 채점은 배포한 앱으로만 한다.
- 깃허브 저장소는 비공개로 만든다. 배포 전에 Streamlit Workspace settings > Linked accounts에서 Private access 옆 "Connect here"를 누른다.
- 배포 뒤 앱 Settings > Sharing에서 "Who can view this app"을 "This app is public and searchable"로 바꾸고 저장한다. 시크릿 창으로 배포 주소를 열어 로그인 화면이 보이는지 확인한다.
- 배포 화면 Branch 칸에는 `master` 또는 `main`, Main file path 칸에는 앱 파일 이름(예: `streamlit_app.py`)을 넣는다.
- Secrets 칸은 `이름 = "값"` 꼴로 쓴다. 브라우저 자동 완성이 예전 값을 채우면 지우고 다시 쓴다.
- 앱은 12시간 방문이 없으면 잠든다(채점자가 깨움, 감점 없음). Supabase 무료 프로젝트는 1주일 동안 DB 요청이 적으면 일시정지되고, 주인만 다시 켤 수 있다. 채점 기간에 일시정지되어 있으면 시나리오 점수 0점이다(13절 16번).
- 일시정지를 막는 방법: 마감 날(11/2)에 배포한 앱에 로그인해 명단을 올리고 지원과 투표를 몇 번 한다. 예고 메일을 받으면 대시보드에서 프로젝트를 열거나 앱을 쓴다. 이미 일시정지되었으면 채점 기간 전에 다시 켠다. 자동으로 막으려면 9절 8번의 어려운 해결을 쓴다.
- 배포 서버 시각은 UTC다. 화면에 시각을 보여 주려면 한국 시각으로 바꾼다.
